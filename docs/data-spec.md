# Synthetic Data Specification (v1.0)

All data in this project is synthetic. It is generated by code in `ml/` and never comes from a real company.
The generator also feeds Project 2 (journal entry anomaly detection), so the schema is kept general.

## 1. Goals
- Produce bank statement lines whose true matches (invoices) are known, so labels are free.
- Include what makes reconciliation hard: missing or noisy references, partial and grouped payments,
  bank fees, and Arabic/English partner name variants.
- Be reproducible: the same `seed` and config always produce the same dataset.

## 2. Entities

### company
| field | type | notes |
|---|---|---|
| company_id | int | |
| name | str | fake |
| country | str | `JO` or `SA` |
| currency | str | `JOD` or `SAR` (one currency per company in v1) |

### partner
| field | type | notes |
|---|---|---|
| partner_id | int | |
| company_id | int | |
| name_en | str | e.g. "Al Noor Trading Co." |
| name_ar | str | e.g. "شركة النور للتجارة" |
| payer_profile | enum | `punctual`, `late`, `partial_payer`, `batch_payer` |
| avg_days_to_pay | float | mean days from invoice date to payment |

### invoice
| field | type | notes |
|---|---|---|
| invoice_id | int | |
| company_id, partner_id | int | |
| number | str | e.g. `INV/2025/00042` |
| invoice_date, due_date | date | |
| amount_total | decimal | 3 decimals for JOD, 2 for SAR |
| currency | str | same as company |

### bank_line
| field | type | notes |
|---|---|---|
| line_id | int | |
| company_id | int | |
| date | date | value date |
| amount | decimal | positive = money in |
| payment_ref | str | free text from the payer or bank, noisy |
| partner_name_raw | str | name as printed by the bank, noisy, Arabic or English |

### match (ground truth)
| field | type | notes |
|---|---|---|
| line_id | int | |
| invoice_id | int | |
| allocated_amount | decimal | part of the line applied to this invoice |

One bank line can map to several invoices (grouped payment). One invoice can be paid by several lines
(partial payments). Some bank lines have no match (fees, unrelated transfers).

## 3. Generation process
1. Create companies, then partners per company with a payer profile.
2. Generate invoices over a date range (default 24 months) with a seasonal volume pattern.
3. For each invoice, sample a payment behavior from the partner profile:
   - **full**: one payment after `avg_days_to_pay` ± noise
   - **partial**: 2–3 payments that sum to the total
   - **grouped**: combined with other open invoices of the same partner into one transfer
   - **unpaid**: stays open (acts as a distractor candidate)
4. Turn each payment into a bank line, then apply the noise rules below.
5. Add unmatched lines (bank fees, salaries, internal transfers) at a set rate.

## 4. Noise rules
| rule | default rate | effect |
|---|---|---|
| missing reference | 30% | `payment_ref` has no invoice number |
| reference typo | 10% | one character dropped, swapped or replaced |
| reference format change | 15% | `INV/2025/00042` → `inv 42`, `INV2025-42`, `00042` |
| bank fee deduction | 8% | amount reduced by a fixed fee (1–5 JOD / 5–25 SAR) |
| rounding difference | 5% | amount off by a small rounding difference |
| name language switch | 40% | bank shows the Arabic name instead of the English one, or the reverse |
| name noise | 20% | truncation, missing "Co."/"شركة", letter variants (ة/ه, أ/إ/ا, ى/ي) |
| transliteration | 15% | Arabic name in Latin letters with varied spelling ("Al-Nour" / "Alnoor") |
| standard amounts | 25% of invoices | invoice billed at one of 4 company-wide standard amounts (look-alike distractors) |
| third-party payer | 3% | `partner_name_raw` is a different partner (e.g. parent company pays) |

All rates are config values, so they can be raised if the data looks too clean.

## 5. Splits
Time-based to prevent leakage: train on months 1–16, validate on 17–20, test on 21–24. No random split.

## 6. Output
Parquet files per entity under `data/generated/<dataset_version>/`, plus a `config.json` holding the seed and
all rates. Generated data is not committed to git.

## 7. Open points
- Arabic name source: hand-written lists of name parts are preferred, because Faker's Arabic company-name
  coverage is not yet checked.
- Multi-currency is out of scope for v1.
